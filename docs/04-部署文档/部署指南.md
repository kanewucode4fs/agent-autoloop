# 部署指南

## 部署形态

支持原生 Windows、macOS、Linux。一台电脑可以同时跑中台、接单程序和通道；接单电脑也可以单独运行 worker 并连接另一台中台。

当前没有 Dockerfile、Compose 文件或前端构建产物，不应把模板中的 Docker 步骤当成现有部署方式。卡片表单由中台提供，中控页面尚未实现。

## 前置条件

| 条件 | 要求 |
| --- | --- |
| Node.js | 24 或更新；本地开发还需 npm |
| Git | 安装、更新与插件克隆使用 |
| CLI Agent | 已安装且由本人完成登录；默认检测 Claude Code 和 Codex |
| macOS/Linux | shell、curl；常驻分别使用 launchd / systemd 用户服务 |
| Windows | PowerShell 5.1、任务计划程序、Windows Script Host |
| 可选工具 | GitHub 场景需要 gh；飞书、浏览器等按对应插件与业务配置 |
| 网络 | 下载代码及所选 Agent / 平台需要的网络；本机默认仅监听 127.0.0.1 |

不要代替用户读取或复制 Agent 登录凭据。Homebrew node@24 若不在 PATH，先按[安装说明](../../INSTALL.md)配置当前 shell。WSL 按 Linux 处理，桌面通知不会自动到 Windows。

## 先确认安装来源

当前 install.sh/install.ps1 默认公共来源仍为 KKKKhazix/agent-autoloop；用户维护的项目仓库为 kanewucode4fs/agent-autoloop。两者不能混为一个已部署版本。

- 默认公共来源：安装器选最新正式 vX.Y.Z tag；update 也按正式版本更新。
- 自定义 URL / 本地仓库：安装器克隆该来源；update 使用该安装副本 origin 的 git pull --ff-only。
- 本地仓库安装的是已提交 HEAD，不含未提交工作区文件。
- 修改 AGENT_AUTOLOOP_REPO 不会改变已经安装副本的 origin；不要在开发工作区里用 update 当成切分支命令。

本指南优先给出本地仓库安装与直接源码运行。通用公开安装入口及 Windows 细节见[INSTALL](../../INSTALL.md)。

## 从本地仓库安装

以下 /path/to/agent-autoloop 必须换成要部署的真实、已提交仓库。安装器把程序放进数据根的 app，配置和数据库留在数据根。

macOS / Linux：

```bash
AGENT_AUTOLOOP_REPO=/path/to/agent-autoloop sh /path/to/agent-autoloop/install.sh --agent codex
agent-autoloop --version
agent-autoloop doctor
```

Windows PowerShell：

```powershell
$env:AGENT_AUTOLOOP_REPO = 'C:\code\agent-autoloop'
& 'C:\code\agent-autoloop\install.ps1' --agent codex
agent-autoloop --version
agent-autoloop doctor
```

选 Claude 时用 --agent claude。不指定 Agent 时检测本机现有的 Claude Code / Codex。其他 CLI 用 --command '某个程序 {prompt}'；找不到程序会停止安装，不会声称已经可用。

## 源码开发和手动运行

在当前仓库根执行；这里运行的是当前文件，适合验证未提交文档对应的实现。npm ci 只安装类型检查和格式化工具，生产运行没有外部 npm 包依赖。

```bash
npm ci
node bin/agent-autoloop.ts --help
node bin/agent-autoloop.ts init --agent codex --no-service
node bin/agent-autoloop.ts up
```

init 会写默认数据目录，已有 config.json 时拒绝覆盖。已有安装或要做隔离验收时，必须先设置独立 AGENT_AUTOLOOP_HOME 和空闲端口，不要直接照抄 init 到正在使用的数据目录。

up 持续前台运行；另开终端用同一 AGENT_AUTOLOOP_HOME 执行 status、doctor 和 try。Ctrl+C 结束手动运行的 up。要注册系统服务再运行 service install。

## 配置和数据文件

默认数据根是 ~/.agent-autoloop，Windows 对应 %USERPROFILE%\.agent-autoloop。

| 路径 | 内容与维护方式 |
| --- | --- |
| app/ | 安装器克隆的引擎代码；源码直接运行不要求此目录 |
| config.json | 本机 URL、hub、worker、source、owner 和通道凭据 |
| rules.json | 来源、Agent、通道、规则、elsewhere |
| secrets.env | Webhook 验签等插件的秘密；不提交 Git |
| master.key | 推导轮次和卡片 token 的主密钥；必须和数据库一起备份 |
| hub.db、hub.db-wal、hub.db-shm | SQLite 日志、投影及运行时 WAL 文件 |
| worker/runs/ | 本地执行与待交结果；完成输出保留 14 天 |
| plugins/ | 本人安装的可信插件，优先于内置同名插件 |
| logs/up.log | macOS / Windows 后台日志 |
| up.pid | 防止同一数据根重复启动的进程记录 |
| try/ | 首次问答试跑的工作目录 |

Unix 数据根限制为 0700，配置和主密钥等私有文件使用 0600；Windows 用本人和 SYSTEM 的 ACL。备份同样含敏感信息，不放进仓库或公开附件。

## 配置项

### 环境变量

| 变量 | 默认 / 用途 |
| --- | --- |
| AGENT_AUTOLOOP_HOME | 默认用户目录下 .agent-autoloop；隔离另一套配置和数据 |
| AGENT_AUTOLOOP_RULES | 默认数据根 rules.json；指定规则文件 |
| AGENT_AUTOLOOP_REPO | 安装器的代码来源；不重写已有安装来源 |
| AGENT_AUTOLOOP_PUBLIC_URL | 运行环境的卡片链接外部基址；up 按 hub.publicUrl 设置 |
| AGENT_AUTOLOOP_SECRET_<来源名> | 适配器验签秘密；来源名大写，连字符转下划线 |
| AGENT_AUTOLOOP_COMMIT / RELEASE | 解包部署声明运行提交 / 版本；常规 Git 安装自动读取，不手写固定版本 |
| NO_COLOR | 控制 CLI 的颜色输出，适合管道和文本采集 |

worker 向子进程提供的资料文件变量等属于插件执行约定，见[插件教程](../plugins.md)；不要把子进程变量当成本机长期配置。

### config.json

| 字段 | 用途 |
| --- | --- |
| url | 本机 CLI、worker、通道连接的中台地址 |
| hub.listen | 监听地址，必须含主机和端口；默认初始化为 127.0.0.1:3350 |
| hub.publicUrl | 卡片链接让接收者访问的地址；默认本机 URL |
| worker.name / key | 此电脑接单身份，与 rules 中 Agent 的 worker 匹配 |
| worker.capacity | 本机可同时运行的轮数，默认 2 |
| worker.unreachable | 本机不可使用的 Agent 列表 |
| source.name / key | 本机 emit / tell 的默认来源 |
| owner | 本机本人权限；只接活的电脑不应有这把密钥 |
| channels | 本机启动的通道、密钥和插件选项 |

rules.json 的业务字段见[使用手册](../05-使用手册/使用手册.md#规则字段速查)和[协议规则](../protocol.md#规则)。config.json 和 rules.json 的通道登记必须配合，不能只配一边。

## 常驻服务

| 系统 | 机制 | 看日志 |
| --- | --- | --- |
| macOS | 当前用户 launchd LaunchAgent | ~/.agent-autoloop/logs/up.log |
| Linux | systemd --user 服务 | journalctl --user -u agent-autoloop |
| Windows | 当前用户登录任务，通过 wscript 隐藏启动 | %USERPROFILE%\.agent-autoloop\logs\up.log |

安装 / 停止当前安装的服务：

```bash
agent-autoloop service install
agent-autoloop service remove
```

service remove 是移除本安装服务，不删业务数据；手动运行的 up 也需要确认已停止。非默认数据根的服务名带路径派生后缀，日志查询以 doctor 打印的命令为准。

Windows 需要真实登录桌面会话；内置 Administrator 在 UAC 下使用的替代办法由命令打印，不能为方便而提权运行所有 Agent。Linux 没有用户服务管理器或 CI 临时环境使用 --no-service。系统级服务由其管理者维护，update 不会另外建一套用户服务替换它。

## 接另一台电脑

1. 在中台机器建立专用 worker 密钥：agent-autoloop key new worker build-box。输出是秘密，应通过私有方式交付，不粘贴到文档。
2. 在新电脑执行下面的命令，或使用安装器的 join 模式。
3. 在规则里把需要远程执行的 Agent 的 worker 设为 build-box，cwd 按远程电脑的真实路径填写。
4. 用中台 status 确认上线，用受控任务验证实际 Agent。路径不由中台电脑解释。

```bash
agent-autoloop join https://hub.example.com --worker build-box --key '<worker-key>'
```

示例中的 <worker-key> 是需要替换的占位符，应先换成通过私有方式取得的实际密钥。只有 worker 配置的新电脑看不了本人全局状态。join 拒绝覆盖已有 config.json。

跨电脑访问需要本人配置监听和网络入口。默认回环地址不能给远端用；公网使用 HTTPS 的受控入口。中台不自动创建反向代理、证书或开放防火墙。

## 部署验证

```bash
agent-autoloop --version
agent-autoloop doctor
agent-autoloop check
agent-autoloop rules explain
agent-autoloop try
agent-autoloop status
```

健康检查访问实际配置的 /healthz，返回 ok 和 commit；仅 HTTP 200 不证明 Agent、通道或业务已经可用。try 会使用真实 Agent 额度，验证提问、退出等待、本人回答和续办；非交互终端会打印回答命令后退出，这是正常等待。

网页业务还需要用同一后台启动方式核对浏览器工具、目标页面和会话续办。try 不验证浏览器，也不验证真实飞书消息、GitHub 发布或第三方账号权限。

## 隔离验收要求

使用临时 AGENT_AUTOLOOP_HOME、随机空闲端口和 --no-service。未验收桌面通知时，在启动 up 前从 config.json 和 rules.json 的 channels 同时移除 desktop。

要验证通知时把假通知命令放在 PATH 最前面。飞书用假 CLI，通道用本地假 HTTP；不要给已经在线的应用再开监听或发真消息。保存本次 up 的 PID，正常、失败和中断均先等该进程退出再清临时目录。

安装冒烟脚本使用临时 HOME、已提交代码和假的 Agent / 通知程序，不能替代真实桌面登录服务验收。真实交付脚本会创建并删除指定私有测试仓库，只有用户明确要求时才执行。

## 日志与故障排查

目前 up 的运行日志为 ISO UTC 时间和组件名，例如 [hub]、[worker]、[desktop]，stdout/stderr 由服务管理器收集。它尚不是包含级别、行号和线程的统一结构化日志，不把全局目标规范写成已经实现。

| 现象 | 先看什么 | 处理方式 |
| --- | --- | --- |
| 没找到 Agent | init 报错、CLI 是否已安装登录 | 在同一用户环境确认程序可启动，或配置完整路径 |
| 已安装 / join 拒绝 | 当前 AGENT_AUTOLOOP_HOME 的 config.json | 核对目标，备份后手动调整，不能反复覆盖 init |
| 无法监听端口 | hub.listen、占用和服务日志 | 更换空闲端口并同步 url / 本机 publicUrl |
| Windows listen EACCES | 系统保留端口 | netsh int ipv4 show excludedportrange protocol=tcp |
| 规则没有生效 | check 输出和规则错误卡片 | 修正文件；坏规则期间旧配置继续运行 |
| 问题未通知 | doctor、通道 lastFailure、是否图形会话 | 修复通道或在 status 中处理卡片 |
| 任务排着不动 | worker 在线、并发、暂停、额度和 notBefore | 按状态排查，不直接改数据库或清 entry |
| 不确定是否在跑 | why、worker 输出及进程 | unknown 不能当成已完成或马上重跑 |
| master.key 损坏 | 启动报错 | 优先恢复完整备份；新建密钥会让既有能力链接失效 |
| 服务管理器不可用 | 当前登录 / 用户服务会话 | 使用 --no-service 和前台 up |
| 更新后还显示旧提交 | /healthz 的 commit、服务来源 | 重启实际运行的服务；系统级服务按提示操作 |

日志、配置、运行输出和备份都可能含私有业务信息。报告问题时删去密钥、Authorization、Cookie 及业务原文，不上传整份数据根。

## 备份、恢复和回退

```bash
agent-autoloop backup /path/to/private-backup
agent-autoloop service remove
agent-autoloop restore /path/to/private-backup
agent-autoloop service install
```

备份目录必须未被占用。backup 使用 SQLite 备份机制，可在中台运行时取得一致数据库，并复制存在的 master.key、config.json、rules.json 和 secrets.env；不包括 app、插件和 worker 输出。

恢复前必须确认中台真的停止，不能只移走 up.pid。restore 校验备份、保留被替换文件在 `restore-before-<时间>`，替换期间失败会尝试还原。非交互恢复需要 --yes，属于明确覆盖操作，不能自动对用户实际数据执行。

恢复后核对 healthz、规则和状态再接业务。需要退回代码时，先根据实际安装来源选择已验证提交，同时保留数据库及主密钥；没有通用的一键“数据库降级”。本项目不编写数据迁移文件。

## 更新和卸载

agent-autoloop update 按本安装 origin 更新并在适用时重启服务；用 --version 和健康 commit 核对实际版本。当前开发分支与未提交修改不应使用生产更新命令维护。

agent-autoloop uninstall 确认后移除自己的程序、链接和服务，保留配置、密钥和历史。非交互用 --yes 也保留数据。不要为了重装删除用户数据目录。

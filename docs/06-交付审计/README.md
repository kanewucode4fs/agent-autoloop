## 一份记录至少写清什么

| 内容 | 要求 |
| --- | --- |
| 目标与范围 | 本次要证明什么，读了哪些文件，改了什么 |
| 基线 | 分支、完整 HEAD、时间、操作系统和工具版本；未提交修改另列 |
| 证据 | 文件路径、实际命令、退出状态、通过/失败/跳过数 |
| 差异 | 需求、业务、技术、部署和手册哪些地方受影响 |
| 限制 | 未跑的环境、真实平台、模拟、安装或发布验证 |
| 结论 | 本次范围内是否完成，未解决问题和下一步 |

只列测试总数不足以判断覆盖：应按测试模块给用例数，新增和端到端场景逐条列出；性能数字写环境与口径，不能作为新发布门槛。

## 记录类别和命名

- 文档或专项审阅：YYYY-MM-DD-主题.md，陈述本次实际范围，不签发交付通过。
- 正式交付检查：delivery-check-YYYY-MM-DD[-suffix].md，由实际执行的 dev-delivery-check 流程归档。
- 同日多次核验使用清晰的 suffix；旧记录保留，不用后来的结果覆盖失败历史。

正式交付检查的步骤和结论以对应技能为准，不能拿本文件替代流程。当前项目处于 iteration，spec/plan 与代码应双向核对；不存在的页面设计不能当成已验收的实现。

## 状态与发布边界

一轮 outcome=done 只表示该轮结束；卡片 decided 只表示本人决定已记录；交付 delivery=success 也需要区分仅审查、仅合并、文档无需上线和实际 live。[状态与转换](../state-machines.md)列明各自权威条件。

本目录存在报告不代表创建过标签。只有正式流程通过且完成规定的复验时才创建对应交付标签；推送、合并和发布分别按用户授权及[项目规则](../../AGENTS.md)执行。文档审阅不打交付通过标签。

## 如何复核本轮文档

1. 从[总索引](../00-总索引.md)进入五份正文，确认内容与当前能力和后续页面计划分开。
2. 沿每条需求和技术说明的代码 / 测试链接核对实现。
3. 复核协议、插件和状态机之间的引用及兼容含义。
4. 查看本轮审阅记录中的实际检查结果和没有覆盖的部分。

## 后续补充时机

页面设计、接口行为、安装形态或交付机制变化后，更新受影响正文并记录实际核验结果。需要正式交付审计时再执行 $dev-delivery-check；不要自动重跑真实账号场景，也不要为了“补证据”向真实通道发消息。

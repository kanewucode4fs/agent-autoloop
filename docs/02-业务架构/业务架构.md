# 业务架构

## 业务目标

把一件事从“发生了”跟进到“做完了”或“确实需要本人决定”，减少人反复叫 Agent、找执行进度和转述决定的次数。中台保留事情的来龙去脉，业务判断和实际动作仍由 Agent 及外部程序完成。

本文说明当前流程。功能和验收行为见[需求文档](../01-需求文档/需求.md)，字段定义见[协议](../protocol.md)。

## 角色和入口

| 角色 | 负责什么 | 入口及权限 |
| --- | --- | --- |
| 本人 | 配规则、定权限、拍板、查全局、停止和暂停 | CLI、本人 HTTP、MCP；使用本人密钥 |
| 事件来源 | 把业务变化变成事件，查询自己事件的结果 | HTTP 事件接口、来源插件、轮询脚本；来源密钥 |
| 中台 | 记事件、归事项、排队派活、记回执、安排到期 | 被动接受请求；不连接外部产品 |
| 接单程序 | 领取指定 Agent 的任务、启动进程、跟踪和提交结果 | work/started/result；接单密钥和本轮 token |
| Agent 或脚本 | 按可信规则处理资料，输出最终结论和回执 | 本机进程；业务工具与授权来自其运行环境 |
| 通道 | 领取卡片、发给本人、核验点击、回报送达 | 卡片领取及回答接口；通道密钥 |
| 外部业务系统 | 保存业务的最终事实，例如 PR 是否合并 | 由插件或任务按各自授权访问，中台不代管凭据 |

## 六个核心对象

| 对象 | 业务含义 | 怎样辨认 |
| --- | --- | --- |
| 事件 | 发生了一件需要记录的事 | 来源 + 来源内编号 |
| 规则 | 哪些事交给谁、去哪里、照什么做 | 唯一规则名 |
| 事项 | 同一规则下要持续跟进的一件事 | rule + lane；未配 parallel 时 lane 为空 |
| 一轮 | Agent 领一批资料、执行、交一次结果 | 中台分配的 run 编号 |
| 回执 | 本轮向中台说明结果和后续安排 | outcome、summary 及 ask/notice/resolve/later/events |
| 卡片 | 发给本人的问题或通知 | card 编号、内容和当前版本 |

事项不是一张独立的“任务表”，没有统一的完成状态列。它由轮次、卡片和未来复查共同表达。页面后续显示任务时需要保留这些区别，不能直接把最后一轮 done 当成事项彻底做完。

## 总体闭环

```text
来源产生事件 → 规则匹配 → 同事项合并排队 → 接单程序领取
                                                  ↓
                                          Agent 读取资料并执行
                                                  ↓
                                            提交最终回执
                       ┌──────────────────────────┼───────────────────┐
                       ↓                          ↓                   ↓
                   本轮做完                  约定到期复查          提问卡片
                       ↓                          ↓                   ↓
                 可发下一步事件               到期产生事件         本人回答
                       └──────────────────────────┴───────────────→ 原事项再排一轮
```

没有下一步事件、未来复查或未结卡片时，这次跟进才没有已登记的后续。中台不会自行推断业务是否全部完成，Agent 必须把需要继续的工作写进回执。

## PROC-1 配置和启用

1. 本人安装并登录 CLI Agent，初始化中台或加入已有中台。
2. 在 rules.json 登记来源、Agent、通道和规则；在 config.json 配本机角色及凭据。
3. 用 check 校验规则、rules explain 查看实际指向，emit --dry-run 预演匹配。
4. 启动 up 或安装当前用户的服务。中台监视规则变化，合法修改生效；坏文件保持原规则并通知。
5. 用 doctor 和 try 验证接活与问答闭环，再启用实际业务场景。

规则和凭据用途不同：规则决定业务行为，config.json 决定这台电脑怎样连接，secrets.env 放来源验签等插件需要的秘密。

## PROC-2 从事件到一轮任务

1. 来源提交 id、type 和资料；中台按来源身份记录，拒绝冒充和坏字段。
2. 命中 when 的规则各自接事件。没有命中也保留记录，便于本人发现漏配。
3. 事件归入规则事项；同事项已有排队轮次时并入，有在跑轮次时排后续一轮。
4. 组、规则、Agent 上限和 worker 容量允许后，接单程序才能领取。
5. 本轮领取时固定 Agent、目录、权限等执行配置；外部事件的 summary/detail 作为资料文件，不拼入提示词。

定时、本人回答、later 到期、手动 run 和 Agent 发出的后续事件，都走事件和事项体系，不另建一套队列。

## PROC-3 执行与回执

1. worker 保存领到的 Job 和本地执行记录，再启动受跟踪的进程。
2. Agent 在规则的 cwd 内工作；prompt/skill 是指令，context.json 是资料。
3. 最终第一行写结论；需要后续动作时附 agent-autoloop 回执代码块。
4. worker 解析最终消息、会话和用量，用本轮 token 交结果；中台在一个事务中记下结果及后续安排。
5. 响应丢失时重复提交同内容，不重复执行回执动作。

回执不合法时，支持续接的 Agent 最多重写两次最终消息，业务不重做。仍不合法时作废回执、保留本轮业务结局并通知本人检查输出。

## PROC-4 提问、拍板与续办

1. Agent 遇到规则要求先问的事或本人才能解除的阻塞，写 ask 并结束本轮。
2. 通道领卡片并投递；送达后报告消息 ref 和版本。
3. 本人选择或自由回答。通道身份要在 answerers 范围内，消息 ref 要匹配。
4. 中台只接受第一次回答，卡片变 decided，原事项带回答排新一轮。
5. Agent 条件允许时续接提问会话，处理剩余工作。成功处理回答后卡片变 done。

如果事情自己解决，可用 resolve 结案为 closed，不再等决定。结案与回答互斥；不能既回答又取消同一个问题。

只有普通文本能力的通道可以给卡片表单链接；网页不运行脚本，打开不等于回答，链接自创建起 7 天有效。持链接者能回答这一张卡片。

## PROC-5 复查、失败和恢复

| 情况 | 业务后果 | 接下来谁做什么 |
| --- | --- | --- |
| 正常需要等外部结果 | 本轮结束，later 保留复查 | 到期派回同事项 |
| 临时执行失败 | 该轮回队列并退避 | 中台按 5 分钟起、最长 1 小时重派 |
| 失败期间有同事项新事件 | 合并进重试轮 | 下次一起交给 Agent |
| 连续第 3 次 / 第 10 次失败 | 通知本人 / 停止重派 | 本人决定是否排查并发新事件 |
| Agent 额度暂时用尽 | 限制该 Agent 的派发 | 到恢复时间再派；本人可手动试一轮 |
| 需要恢复连接、登录或验证 | 用 done + ask 结束本轮 | 本人处理并回答后只做剩余步骤 |
| worker 重启 | Agent 可能仍在跑 | 从本地记录恢复跟踪，不直接重做 |
| 单轮久未上报 | unknown，不等同于失败 | 通知本人，迟到结果仍可提交 |
| worker 整台离线 | 未确认的活保留 | 恢复后继续跟踪 |
| 本人停止一轮 | 停整个进程树 | 确认进程退出后取消，不自动重派 |

不该反复用 later 探测额度、登录或本人才能解决的阻塞。长会话续接有费用，长时间的外部恢复探测宜用脚本规则，恢复后再发事件唤醒 Agent。

## PROC-6 暂停和有选择地补跑

暂停表示“这条规则暂时不做新动作”：

- 已领取的一轮继续执行；需要马上停用 stop。
- 原队列、回答和复查保留，暂停时不派发。
- 新来源事件照常记下，但此规则跳过，不积压。
- 定时触发直接跳过，恢复后从下一个时刻继续。

resume 解除暂停并列出跳过事件；本人确认需要追补时，用返回的 since 执行 replay。每条事件对同一规则只补一次。暂停时不允许 replay 或 run 绕过暂停。

## PROC-7 PR 从交付标签到结果

1. 配置的轮询程序读取 GitHub 标签，产生稳定编号事件；一个 PR 对应一个事项。
2. 交付 Agent 从固定 main 提交读配置和审查点；PR 代码仅转换成文字快照供审查。
3. 必要时同步 main，审查分支自己的改动；挡上线问题退回，建议只记录。
4. 等当前 head 的最新 pull_request 工作流及所有必需 job 成功。草稿和 skipped 检查不能放行。
5. 合并前重读 head、base、main、标签和自动合并状态；发生变化就按流程重来或结束本轮。
6. 合并后等 Ship 覆盖合并提交，核对健康版本后报告上线；无健康设置时只报告合并。
7. deliver-review 只完成审查；撤回交付、退回修改、待本人决定都有独立结果，不冒充 live。

交付的完整条件、重试次数、可信审查记录和发布判断见[协议交付插件](../protocol.md#交付插件)。

## 信息流与可信边界

| 信息 | 从哪里来 | 到哪里去 | 限制 |
| --- | --- | --- | --- |
| 规则和任务说明 | 本人维护的规则 / Skill | 中台判断、worker 提示词 | 不能由事件改写 |
| 事件资料 | 外部来源 | 日志、资料文件、状态输出 | 可含不可信文字，Agent 应视为资料 |
| 回执与回答 | Agent / 本人 | 事实日志及下一轮资料 | token、卡片范围和身份核对 |
| 平台凭据 | 本机私有配置 | 真正连接平台的插件 | 不由内核收集或转交 Agent |
| 状态快照与事实流 | 中台 | 本人客户端 | 本人密钥；快照 seq 后续读 SSE |
| PR 设置 | 固定 main | 交付 Agent | PR 自身设置不能授权执行 |

## 核心业务规则

- 来源、事项、轮次、卡片的编号和身份不得混用。
- 一轮结束不等于事项结束；决定已记录不等于决定已执行。
- 重试、回答和复查都保留原事项，不能因规则并发调整落到别的事项。
- 同一轮回执的副作用原子生效；失败回执不生效提问、复查和新事件。
- 外部业务动作必须自行幂等；不能把事件去重当成外部动作恰好一次。
- 中控页面属于后续本人客户端，当前业务不能依赖尚不存在的页面。

# 使用手册

## 适用读者

已经安装 Agent Autoloop、希望让命令行 Agent 自动处理任务的人。还没安装先读[部署指南](../04-部署文档/部署指南.md)。开发新插件看[插件教程](../plugins.md)，查完整数据字段看[协议](../protocol.md)。

当前使用命令行、消息通道和卡片表单；没有可以打开的任务总览页面。查看所有任务的中控页面是下一阶段计划。

## 首次跑通：提问、拍板、接着做

安装时选好的 Agent 必须已经登录，且 up 或后台服务正在运行。

1. 运行 agent-autoloop doctor，检查中台、Agent 和通道是否接通。使用 --no-service 的开发环境出现“服务未运行”并不代表中台没开。
2. 运行 agent-autoloop try。试跑只要求 Agent 问一个颜色问题，不改业务文件，但会使用模型额度。
3. 交互终端直接选蓝色或绿色；非交互环境显示问题后退出，按打印的 answer 命令回复，再用 status 查看“试跑通过”。

```bash
agent-autoloop doctor
agent-autoloop try
agent-autoloop status
```

看见问题但没有“试跑通过”还不能认为闭环接通。需要网页操作的任务另外验证后台浏览器工具，try 不验证浏览器或第三方账号。

## 日常先看哪里

```bash
agent-autoloop status
agent-autoloop status --json
agent-autoloop runs
agent-autoloop runs "处理待办"
agent-autoloop why 42
```

编号 42 是用法示例，实际替换为 status/runs 给出的轮次。runs 展示做完或不再处于 queued/claimed 的轮次；why 展示事件、规则版本、领取、会话、回执、回答和后续轮次。

| 看到什么 | 代表什么 | 可以做什么 |
| --- | --- | --- |
| queued | 等待领取，可能还在退避 | 看 worker、并发、暂停和时间 |
| claimed | 正在执行 | 用 why 查看上下文，需要时 stop |
| unknown | 久未上报，是否仍在执行不确定 | 查执行电脑，不能直接当失败重做 |
| done | 本轮成功结束 | 继续看未结卡片和未来复查 |
| nothing | 看过了，没有要做的 | 有新变化时仍可触发 |
| cancelled | 停止、规则退役或连续失败达到上限 | 查 summary 和 why |
| 卡片 open | 等回答或处理 | answer 或核实后 resolve |
| 卡片 decided | 决定已记录，续办尚未确认完成 | 看原事项后续轮次 |
| 卡片 done / closed | 决定执行完成 / 已结案 | 二者不是同一个业务意思 |
| 未来复查 | 已安排稍后再看 | 不代表遗忘或阻塞 |

## 配置一条接活规则

规则在数据根 rules.json；默认 ~/.agent-autoloop/rules.json。修改前先保留当前配置，新增条目与现有 sources/agents/channels/rules 合并，不能拿示例覆盖正在使用的整份文件。

下面是一份可校验的结构示例。worker 要换成 config.json 中实际的 worker.name，cwd 换成接单电脑上的真实绝对目录。Agent 的登录凭据不写在这里。

```json
{
  "timezone": "Asia/Shanghai",
  "sources": {
    "local": { "name": "本机" }
  },
  "agents": {
    "codex": {
      "name": "Codex",
      "worker": "my-computer",
      "use": "codex",
      "access": "edit"
    }
  },
  "channels": {},
  "rules": [
    {
      "name": "处理待办",
      "when": { "source": "local", "types": ["task.created"] },
      "to": "codex",
      "cwd": "/path/to/project",
      "prompt": "核对当前状态，处理这件待办；需要本人决定时提问并结束本轮。",
      "tell": "needed"
    }
  ]
}
```

channels 为空的示例只便于解释结构，没有主动通知通道；已有 desktop/feishu 登记要保留。接入通道需同时配置 rules.json 的登记和 config.json 的插件/密钥。Agent 的业务权限以可信规则为准。

保存后先校验和预演：

```bash
agent-autoloop check
agent-autoloop rules explain
agent-autoloop emit task.created --id demo-001 --subject demo-001 --summary "核对待办" --dry-run
agent-autoloop emit task.created --id demo-001 --subject demo-001 --summary "核对待办"
```

dry-run 不连中台、不写事实。正式 emit 会启动真实任务，确认目录和授权后再执行。同来源相同 id 重发只记一次；想表达另一件事要换稳定且不同的编号。

### 规则字段速查

| 字段 | 默认 / 行为 |
| --- | --- |
| timezone | 未写使用系统时区；国内业务建议明确 Asia/Shanghai |
| askFirst | 默认删数据、停服、花钱、对外发消息、改产品方向、新建或轮换密钥、修改权限 |
| sources | 来源 ID 与名字，可为 Webhook 配 adapter |
| agents | Agent ID、worker、use、权限和运行参数 |
| channels / defaultChannels | 可用通道与缺省发送范围；未设 defaultChannels 时使用所有登记通道 |
| rules[].when | source + types，或 cron；事件类型支持 x.* / * |
| to / cwd | 可信的 Agent 与接单电脑工作目录 |
| skill / prompt | 可信任务说明；普通 command 规则可都不写 |
| group | 默认规则名；组内共同控制领取上限 |
| parallel | 未写时整条规则一个事项；写正整数后按 subject 分事项，并限制同组轮数 |
| maxActive | 规则或 Agent 的额外同时领取上限，未写无此额外限制 |
| resume | 默认不续接普通新事件；回答、重派、复查另按原会话约定 |
| tell | needed 默认仅有卡片时；always 每轮做成都通知；never 抑制回执通知，提问及中台告警仍发 |
| emits | 允许回执发的来源与事件类型；不写不能发 |
| channels | 该规则的明确通道范围 |
| title / tags | 会话标题模板、状态和资料标签；不改变派发权限 |
| agents[].access | 默认 edit；read / edit / full 由对应适配器映射 |
| agents[].timeout | 默认 180 分钟，正整数分钟 |
| agents[].model / effort / tier / program | 按适配器支持范围传入，不能假设所有 Agent 都支持 |
| elsewhere | 登记在别处定时运行的任务；中台不负责启动其原始计划 |

同组的 parallel 必须一致。调整 group、Agent 或权限会影响排队任务，已领取的一轮保留领取时的配置。完整语义和限制见[协议规则](../protocol.md#规则)。

## 让 Agent 正确交回执

一轮的最终消息先写一句结论，需要后续动作时加下面的代码块。示例表示“本轮结束，等本人决定”，不是在 Agent 进程中阻塞等回答。

````text
待你处理：需要你确定处理范围。

```agent-autoloop
{
  "ask": [
    {
      "title": "只修复当前问题吗？",
      "text": "已定位当前问题，请确认本次修改范围。",
      "options": ["只修当前问题", "暂不修改"],
      "recommend": 0,
      "about": "回答后只执行选择的范围，保留已经完成的调查。",
      "key": "fix-scope"
    }
  ]
}
```
````

| 字段 | 作用 |
| --- | --- |
| ask | 提问，options 为本人可选项；recommend 从 0 开始 |
| notice | 通知；fyi=true 仅告知，创建时已 closed |
| resolve | 核实问题已解决后结卡片，只限本轮允许范围 |
| later | 按事项的 key 安排、改期或取消复查 |
| events | 触发下一步，来源和类型受 emits 限制 |

临时失败第一行写“没跑成：原因”；没事可做写“没事可做：原因”。需要恢复登录或连接写“待你处理：原因”，交 ask 后结束，保留已完成内容，不反复 failed/later 重试。

只有来源、worker 等程序需要直接发送结构化 Result；普通 Agent 只需最后一条文字和回执代码块。完整字段见[协议回执](../protocol.md#agent领活干活交回执)。

## 回答和结案

```bash
agent-autoloop answer 56 1
agent-autoloop answer 56 --text "按现有配置继续"
agent-autoloop resolve 56 "已核实问题恢复，不再需要决定"
```

卡片编号 56 是示例。CLI 选项从 1 开始，HTTP/MCP 的 choice 从 0 开始。普通通知 answer 不必传序号。resolve 代表“不用再决定”，不能拿来伪装“决定已执行”。

每张卡片只接受一次回答或结案；重复命令不会重复唤醒。本人通过通道回答时，通道还要核对回答人及送达消息，不能只凭卡片编号。

## 停止、暂停、恢复和补跑

```bash
agent-autoloop stop 42
agent-autoloop pause "处理待办" --reason "检查下游后再开"
agent-autoloop resume "处理待办"
agent-autoloop replay "处理待办" --since "2026-11-23T09:00:00+08:00"
agent-autoloop run "处理待办" --subject demo-002 --reason "手动核对"
```

stop 针对一轮，等待进程树退出；pause 针对规则，不停止已领取的轮次。暂停期间来源事件被记录但不为这条规则积压，恢复不自动补发。replay 的 since 应使用本次 resume 打印的实际时间，不使用上面示例时间。

手动 run 仍遵守并发和规则，不能绕过暂停；可用于提前试跑额度是否恢复。要暂时止损，先暂停并明确停止正在跑的轮次。

## 定时任务和长期等待

定时规则使用五段 cron，例如 "0 9 * * *"。时间按规则的 timezone 解释；错过多个时刻只补最近一次。本人暂停期间的时刻不补。

later 用于跟进正在做的同一件事，at 必须是带时区的真实日期。长时间等待外部恢复时，可以用 command 脚本定时探测，恢复后发事件，避免每次把很长的模型会话重读一遍。

elsewhere 只登记外部计划，例如桌面应用的定时任务。它要问本人时还需配置 cwd 与续办指令；回答由中台叫醒对应 Agent，不接外部计划自己的原始会话。

## 安全和常见问题

- **Agent 已完成为什么仍有卡片？** 本轮完成可以等待本人；decided 卡片也可能还在等后续执行，先查 why。
- **为什么同一件事又执行？** 系统是至少一次，任务应先核对业务当前状态。中台的事件去重不替代外部幂等。
- **为什么花费显示缺失？** 适配器未报或续接缺可信基线时保留未知，不把未知当成零。
- **为什么消息没到？** 通道在线只表示在领取，不保证送达，检查 lastFailure 与 doctor。
- **为什么配置里的 cwd 找不到？** 目录在接单电脑上解释，不是在中台机器上解释。
- **为什么后台没有浏览器？** Agent 的桌面工具不必然在后台 CLI 可用，按插件教程实际验收。
- **为什么 MCP 不能给干活的 Agent 配？** 本人密钥能回答卡片等，放进 worker 的用户级配置会让一轮越过本轮权限。
- **去哪里报告问题？** 按[贡献指南](../../CONTRIBUTING.md)提交，附脱敏版本、命令、错误和复现步骤，不上传配置、密钥及业务原文。
